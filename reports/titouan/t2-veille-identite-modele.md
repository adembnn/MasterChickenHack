# T2 Model Equality : un indice sur le(s) modèle(s) réels derrière les 33 endpoints ? (21 nov. 2026)

Décision débloquée : faut-il parier sur une famille de base précise (OLMo) pour orienter M3/M4 (vraisemblance locale, simulateur), ou rester agnostique.
Marques : [CONFIRMÉ] = vu directement (page, dépôt, fichier officiel) ; [PROBABLE] = plusieurs indices convergents, pas une preuve ; [SPÉCULATIF] = une seule source faible ou un raisonnement ; [ÉCARTÉ] = piste vérifiée et qui ne mène à rien. Recherche web uniquement, aucun appel à l'API du hackathon.

## Résumé en une phrase
Aucune édition passée n'a fait tourner exactement ce challenge (interroger 33 API inconnues en boîte noire pour regrouper des LLM) ; le seul indice concret et officiel sur le modèle de base est la phrase d'exemple du sujet lui-même, qui cite OLMo [PROBABLE] — tout le reste (dépôts GitHub, HuggingFace SprintML, papiers MET/RUT/AgentProv, réseaux sociaux) ne donne pas de preuve directe.

## 1. Aucune édition passée n'a fait "Model Equality" tel quel [CONFIRMÉ]
Six qualifications régionales + une finale ont eu lieu entre nov. 2025 et juil. 2026 (Paris, Vienne, Stockholm, Munich, Barcelone, Varsovie, finale St Ingbert/Sarrebruck). J'ai cherché un équivalent de "interroger des endpoints inconnus pour décider s'ils servent le même LLM" dans chacune. Aucune ne colle exactement :
- **Paris (nov. 2025, 1ʳᵉ édition)** : attribution d'images générées à leur modèle générateur (VAR, RAR, Taming Transformers, Stable Diffusion…) — vision, pas texte, pas d'API à interroger [CONFIRMÉ, dépôt `floriandgg/cispa`, repris du org `Loki-Hackathons`].
- **Vienne (13-14 déc. 2025)** : trois tâches — (1) inférence d'appartenance/dataset sur ResNet-18, (2) **"LLM text attribution" : prédire quel LLM a généré un texte donné, sur un jeu de ~85 000 exemples étiquetés fourni d'avance**, (3) suppression de filigrane d'image (BitMark). La tâche 2 est la plus proche cousine de notre T2 : même idée (identifier le LLM auteur d'un texte), mais protocole opposé — un gros dataset étiqueté à classifier (classifieurs DeBERTa-v3/ModernBERT), pas 33 API en boîte noire avec budget de requêtes. [CONFIRMÉ, dépôt `florianzainzinger1/cispa-hackathon-championship-vienna`, équipe gagnante "!1337"]. Le code d'exemple des organisateurs met un nom de modèle en valeur de test (`model_name = "deepseek-ai/DeepSeek-Coder-V2-Lite-Instruct"`), mais c'est un placeholder dans le script d'exemple de soumission, pas une vérité terrain annoncée — à ne pas prendre pour argent comptant [ÉCARTÉ comme indice].
- **Stockholm (févr. 2026)** : trois tâches dont une d'"attribution de modèle", décrite ailleurs comme sur de l'image générative ("model fingerprinting génératif", déjà noté dans `t2-communaute-et-combinaisons.md`) — pas confirmé en détail, pas de dépôt de code trouvé pour vérifier si c'est du texte ou de l'image [SPÉCULATIF, non vérifié davantage].
- **Varsovie, Munich, Barcelone, finale** : tâches connues = inférence de dataset / appartenance, extraction de modèle par shadow model, détection de filigrane texte, watermark removal, reconstruction de données en apprentissage fédéré, inversion de modèle. Aucune ne porte sur "qui sert quoi derrière une API" [CONFIRMÉ par les rapports déjà écrits dans ce dépôt et par les pages officielles CISPA consultées aujourd'hui].

Conclusion de cette section : **pas de réutilisation directe d'une édition passée**. Le plus proche parent est Vienne (tâche 2), mais le protocole (dataset étiqueté vs API à sonder) est différent, donc aucun transfert de "quel vrai modèle était caché" ne s'applique.

## 2. L'entretien des organisateurs décrit le principe général du "model stealing", sans détail [SPÉCULATIF]
Interview CISPA du 10 nov. 2025 avec Boenisch et Dziedzic ([lien](https://cispa.de/en/interview-hackathon-championship)) : Boenisch décrit une tâche-type "basée sur le travail d'Adam" où *"We make our own model, expose the open API and tell them to 'steal it'. Then, at the end, we compare how similar it is to our model."* Aucune ville, aucun nom de modèle, aucune taille n'est donnée. Dziedzic : *"We designed the tasks based on our research"* ; Boenisch confirme que les tâches du cours de Sarrebruck et des hackathons viennent de la même recherche. Ça confirme le style de la maison (toujours un modèle hébergé par les organisateurs derrière une API), pas un modèle précis.

## 3. HuggingFace `SprintML` : une trouvaille à prendre avec précaution
- Le compte HF `SprintML` (org "Trustworthy AI", site sprintml.com) héberge un dataset `SprintML/model_equality` dont les **9 lignes sont identiques, caractère pour caractère, à nos `ref-01..09`** (colonnes `endpoint,family,model,kind` ; famille "P", codes S/T1-T4, mêmes types de déguisement : fp8, LoRA 0,3/0,7/1,5, prompt système, persona, filigrane, température 1,0) [CONFIRMÉ, page consultée aujourd'hui]. C'est bien la source officielle de nos données de pratique — pas une fuite, mais ça ne nomme aucun modèle de base (pas de dataset card, pas de README).
- Le même compte héberge un **modèle `SprintML/tml26_task2`** avec deux dossiers `target_model/` (1 fichier `weights.safetensors` de 44,9 Mo) et `suspect_models/` (360 fichiers `suspect_000.safetensors` à `suspect_359.safetensors`, tous à 44,9 Mo, 16 Go au total) [CONFIRMÉ]. Le nom ("Trustworthy ML 2026, tâche 2") a d'abord semblé très prometteur, mais **44,9 Mo est beaucoup trop petit pour un LLM** (même un modèle d'1 milliard de paramètres pèse plusieurs Go en fp16) : c'est presque certainement un tout autre exercice du cours universitaire "Trustworthy ML" (donné par les mêmes organisateurs), par exemple un petit classifieur pour une tâche 2 de cours sans rapport avec le texte. **[ÉCARTÉ comme indice de modèle]**, mais gardé dans ce rapport pour éviter qu'un autre agent reparte dessus en pensant avoir trouvé le modèle caché.
- Aucun dépôt GitHub de l'organisation SprintML n'a été trouvé (ni "SprintML/model_equality" ni "SprintML/hackathon" sur GitHub) : tout vit sur HuggingFace, pas GitHub, contrairement à l'hypothèse de départ.

## 4. L'indice le plus direct et le plus solide : l'exemple du sujet officiel lui-même [PROBABLE]
`reports/sources/Model_Equality_Testing.txt`, section "Challenge" : *"For example, two deployments of the same **OLMo** base model with the same quantization and adapter settings are identical, even if one uses a decoding watermark and a different system prompt. A quantized variant of that checkpoint, or a version with a different LoRA adapter, is a different model."*
C'est la seule fois où un nom de modèle de base apparaît dans tout le matériel officiel. Pourquoi lui faire un peu confiance, sans trop :
- **Pour** : les auteurs du sujet (Xun Wang, Bihe Zhao, Maitri Shah, Ivo Hoese, Aditya Kumar, encadrés par Dziedzic/Boenisch) auraient pu choisir n'importe quelle famille connue (Llama, Mistral, GPT) pour l'exemple pédagogique ; choisir OLMo (AllenAI) est un choix inhabituel dans la littérature grand public, mais logique pour des organisateurs qui ont besoin de contrôler totalement un "modèle de référence" (poids ET données d'entraînement intégralement publics, plusieurs tailles et checkpoints intermédiaires disponibles, facile à quantifier et à patcher avec un LoRA soi-même) — exactement ce qu'il faut pour fabriquer 33 endpoints avec vérité contrôlée.
- **Contre** : un exemple pédagogique n'est pas un engagement. Rien dans le texte ne dit "les endpoints sont des OLMo". Et les trois papiers de référence du sujet (MET, RUT, AgentProv) **n'utilisent OLMo que de façon secondaire** : MET le cite seulement en annexe (C.1/C.2) parmi des "modèles alternatifs" testés en plus de son trio principal (Mistral-7B-Instruct, Llama-3/3.1 8B et 70B) [CONFIRMÉ, lecture du papier] ; RUT et AgentProv ne le mentionnent pas du tout dans leurs propres expériences (RUT : Llama-3.2-3B, Mistral-7B-Instruct-v0.3, Gemma-2-9B/2B ; AgentProv : famille Qwen2.5/3, Llama-3.1/3.2, Mistral/Nemo/Ministral, DeepSeek, Phi-4-mini, Gemma-3, GLM-Z1, Nemotron-Nano, SmolLM3 — aucun OLMo) [CONFIRMÉ, lecture des deux papiers]. Si les organisateurs avaient simplement recyclé le setup expérimental d'un des trois papiers, OLMo serait un choix bizarre.
- **Verdict** : [PROBABLE] mais pas [CONFIRMÉ]. C'est le seul fait vérifiable qui pointe vers un nom de modèle précis, mais ça reste un exemple didactique, pas une spécification. Ne pas bâtir tout M3/M4 sur ce seul indice ; le traiter comme une hypothèse à tester en premier si on tente la vraisemblance locale (télécharger OLMo-7B ou OLMo-2 en plusieurs quantifications et comparer, avant d'essayer d'autres familles).

## 7. Recommandation pratique
1. Ne pas réorganiser tout le plan M3/M4 autour d'OLMo : c'est un indice [PROBABLE], pas une certitude, et le budget pour télécharger/tester plusieurs familles en parallèle sur les A100 est faible (quelques heures).
2. Si on tente la vraisemblance locale (M3) ou le simulateur (M4, cf. `t2-model-equality-etat-de-lart.md` §3), commencer par **OLMo-7B / OLMo-2** en bf16 + quantifications (nf4, int8, fp8) + un LoRA d'essai, en test gratuit sur les `ref-*` (dont on connaît déjà la vérité : S/T1-T4). Si ça ne colle pas visiblement mieux qu'un autre candidat sur les 9 ref, basculer sur Llama-3.1-8B ou Qwen2.5-7B (les deux styles "maison" des papiers) sans s'entêter.
3. Ne pas perdre de temps sur `SprintML/tml26_task2` (HF) : poids trop petits, presque sûrement un exercice de cours sans rapport — déjà vérifié, inutile de re-creuser.
4. Mettre à jour cette note si quelqu'un trouve un dépôt GitHub de l'organisation SprintML (aucun trouvé à ce jour) ou un post public des organisateurs sur ce challenge précis.
